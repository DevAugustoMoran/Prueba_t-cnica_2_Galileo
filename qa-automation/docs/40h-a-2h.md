# De 40 horas a 2: demostrado con los 4 cambios del mes

Este documento responde una pregunta concreta: **¿por qué la validación humana
mensual baja de ~40 horas a ~2, y no es una promesa — es algo que se puede
verificar?** Se demuestra con los 4 cambios del mes, porque son los que
mejor ilustran la diferencia entre "probar algo a mano" y "que quede probado
solo".

## El cálculo, en corto

- **Antes**: un humano recorre a mano los 12 flujos del scope del examen más
  los 4 cambios del mes, cada mes, en la instancia real. Repetir esto de
  forma confiable — con el mismo cuidado la primera vez que la
  vigésima — es lo que consume las ~40 horas.
- **Ahora**: `npm test` (o la corrida mensual automática en GitHub Actions)
  ejecuta las 20 pruebas de punta a punta contra una instancia recién
  instalada, sin que nadie toque nada, y deja un reporte con evidencia real
  de cada paso.
- **Lo que queda para el humano**: revisar que la corrida haya quedado en
  verde (minutos, no horas) y, únicamente si algo falló, abrir el reporte
  para entender qué cambió. Ese residual — revisión de evidencia, no
  re-ejecución manual de la prueba — es el que ocupa las ~2 horas.

La tabla de abajo hace ese contraste explícito para cada uno de los 4
cambios: qué hace la prueba automática por su cuenta, y qué haría (o
seguiría haciendo) un humano si tuviera que validarlo a mano.

## Cambio 1 — Asistente de IA para calificar ensayos

| | |
|---|---|
| **Qué corre solo** | El test abre la pantalla real de calificación, intercepta la llamada al endpoint de IA (con una respuesta simulada, para no depender de la API real ni de su variabilidad), clickea "Generar Sugerencia", y verifica que el pedido saliente llevó el contenido real de la pregunta *y* que el formulario de calificación quedó precargado con la nota y el comentario correctos. |
| **Validación manual que reemplaza** | Antes: un humano abría la pantalla de calificación, clickeaba el botón, esperaba una respuesta real de la IA (tiempo variable, contenido no repetible de una corrida a otra), y verificaba a ojo que los campos se llenaron. No era 100% reproducible porque la IA responde distinto cada vez. |
| **Qué sigue siendo humano** | Si Anthropic/Google cambian el contrato de su API, o el plugin cambia el formato de respuesta esperado, el test lo detecta (falla) — ahí un humano decide qué hacer, no lo descubre semanas después en producción. |

## Cambio 2 — Señal de integridad por pérdida de foco

| | |
|---|---|
| **Qué corre solo** | El test rinde un examen como alumno, dispara dos pérdidas de foco reales (el mismo evento del navegador que el código real escucha, no una simulación de más alto nivel), y verifica que el profesor ve el badge "Foco perdido: 2" correcto en el reporte de resultados. |
| **Validación manual que reemplaza** | Antes: un humano tenía que rendir un examen, cambiar de pestaña a mano un par de veces con el timing justo para que quedara registrado, y después ir a revisar el reporte del profesor. Delicado de reproducir igual dos meses seguidos. |
| **Qué sigue siendo humano** | Ninguna intervención rutinaria. |

## Cambio 3 — Notificación de resultado a sistema externo

| | |
|---|---|
| **Qué corre solo** | El test envía un intento real y confirma, por fuera del navegador (leyendo directo la bitácora del receptor), que el webhook realmente llegó — con un mecanismo de respaldo determinístico (dispara el cron a demanda) si el envío inmediato no alcanza a tiempo, en vez de asumir que "probablemente llegó". |
| **Validación manual que reemplaza** | Antes: revisar logs del servidor a mano, o directamente confiar en que "no se rompió nada" sin verificación real — el tipo de chequeo que en la práctica casi nunca se hace a mano todos los meses. |
| **Qué sigue siendo humano** | Nada rutinario. Vale la pena notar que, mientras se armaba este test, se encontró un bug real en `receptor.php` (una escritura fallida no se reportaba como error) — quedó corregido, y es exactamente el tipo de cosa que una prueba automatizada real saca a la luz y una revisión visual no. |

## Cambio 4 — Penalización por entrega en período de gracia

| | |
|---|---|
| **Qué corre solo** | El test usa un examen con límite de tiempo corto y período de gracia largo: el alumno responde a tiempo pero entrega después del límite, dentro de la gracia. Se verifica tanto la nota final penalizada como el mensaje real de retroalimentación que arma el plugin (no solo "la nota bajó", sino "bajó por el motivo correcto"). |
| **Validación manual que reemplaza** | Antes: cronometrar a mano una entrega tardía real, y verificar el porcentaje de penalización a ojo contra la configuración del sitio. |
| **Qué sigue siendo humano** | Si se cambia el porcentaje de penalización por defecto (`Configuración del sitio`), el test sigue pasando igual — está escrito para verificar el *mecanismo*, no un número fijo, así que no hace falta tocar el test cada vez que cambia esa configuración. |

## Por qué esto se sostiene, no es una foto de un buen día

Los 4 cambios de este mes no llegaron a pasar en el primer intento contra el
entorno real de CI — en el camino se encontraron y corrigieron problemas
genuinos: un idioma que faltaba instalar, permisos de archivos, un bug de
`set -e` matando un proceso de fondo, timing de cron real. Cada uno de esos
hallazgos quedó resuelto en el código (no evitado en el test), y la corrida
completa quedó verde de punta a punta, repetible, arrancando de una
instancia limpia cada vez. Eso es lo que hace que las ~2 horas mensuales
sean sostenibles el mes que viene también, no solo hoy.
